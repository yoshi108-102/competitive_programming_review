リクエストの旅 — Cognito → API Gateway → Lambda → DynamoDB

ブラウザが送ったリクエストが各 AWS サービスを通過する様子を、トグルで条件を変えながら体験するデモです。JWT・CORS・Lambda Proxy 統合の「失敗パターン」も再現できます。

🌐 Cognito 🚪 API Gateway ⚡ Lambda 🗄️ DynamoDB

コントロール — 条件を切り替えてリクエストを送信

JWT を付ける (Authorization: Bearer <token>)
OFF にすると API Gateway Authorizer が 401 を返し、Lambda まで届かない
Origin を許可リストに入れる
OFF にすると OPTIONS プリフライトで CORS エラー — ブラウザが本リクエストをブロック
body を json.dumps で文字列化する
OFF にすると Lambda が dict のまま返し、API Gateway が 502 Malformed Lambda proxy response

学ぶポイント

  • Lambda Proxy 統合の契約: body は「文字列」必須 handler の戻り値 body は json.dumps した文字列でなければならない。dict のまま返すと API Gateway が 502 Malformed Lambda proxy response を返す → shared/response.py で json.dumps を強制する理由
  • CORS プリフライト Authorization ヘッダ付きリクエストは Simple Request 条件を外れるため、本リクエスト前に OPTIONS が飛ぶ。サーバの Access-Control-Allow-Origin が不許可なら本体は届かない
  • JWT(Bearer) 認証と CSRF 耐性 ブラウザが自動付与する Cookie と違い、Authorization ヘッダは JS が明示的に付与する。自動送信ルートが無い = CSRF に構造的に強い
  • DynamoDB 書き込み: float → Decimal 変換 PK/SK で 1 アイテムを特定。Boto3 は float を拒否し Decimal を要求する。数値型は必ず Decimal(str(val)) に変換してから put_item に渡す
