DynamoDB = 分散ハッシュテーブルという視点

概要

DynamoDB を「分散ハッシュテーブル（Distributed Hash Table, DHT）」として捉え直すメンタルモデルをまとめる。データ構造的な見方（ハッシュマップ + パーティション内ソート構造）を握ると、DynamoDB の制約（PK完全一致のみ、JOIN不可、集計苦手、GSIがコピー、など）がすべて「ハッシュテーブルの性質」から自然に導けるようになる。

RDB との比較で押さえた「アクセスパターン駆動設計」「非正規化」「GSIの存在意義」といった知識を、より下位のアルゴリズム/データ構造レベルで一貫して説明できる視点。

解説

1. DynamoDB のデータ構造的な正体

競プロ風に C++ で書くなら以下の構造:

// 各サーバー上の構造
map<string /* PK (hash) */, map<string /* SK */, Item>> partition;

// ただしPKは直接hashされて「どのサーバーに置くか」も決まる
// → unordered_map<PK, map<SK, Item>> が物理的に複数サーバーに分散

つまり:

  • PK 空間 = unordered_map（ハッシュで分散、完全一致のみ、O(1)）
  • 同じPK内のSK空間 = map（ソート済み、範囲クエリOK、O(log n)）

「永続化されて、分散されている巨大なハッシュテーブル」という一言で表せる。

2. 制約の正体が全て説明できる

DynamoDBの制約ハッシュテーブル的な理由
PKは = 完全一致のみハッシュ関数で分散してるので、範囲検索はハッシュ値空間上で意味がない
PKの値は変更不可値を変えるとハッシュ値が変わる → 置き場所が変わる → 実質削除＋再挿入
SKは範囲クエリOKパーティション内は map / B-tree でソート済み
GSIは別のコピー別のキーでハッシュし直す = 別の物理配置が必要
ホットパーティション問題ハッシュの偏りそのもの。PKのカーディナリティ低い＝バケット偏り
JOIN不可ハッシュテーブルは関係演算のための構造じゃない
集計苦手ハッシュテーブルで COUNT, AVG は全走査するしかない

「ハッシュテーブルの性質」がほぼそのまま DynamoDB の仕様になっている。

3. 歴史的背景: Dynamo 論文 (2007)

DynamoDB の起源は Amazon 社内ペーパー:

"Dynamo: Amazon's Highly Available Key-value Store" (SOSP 2007)

これは分散ハッシュテーブルの実装論文で、以下のアルゴリズムを組み合わせている:

要素アルゴリズム解決する問題
データ配置Consistent Hashing（一貫性ハッシュ法）サーバー追加/削除でもデータの再配置を最小化
障害耐性Vector Clock + Quorumネットワーク分断下での整合性
負荷分散Virtual Node（仮想ノード）ハッシュ偏りを緩和
複製N-R-W (Replication)レプリカ数、読み書き quorum

この論文の子孫:

  • Apache Cassandra（Facebook発、Dynamo + BigTableの合成）
  • Riak
  • Voldemort（LinkedIn）
  • ScyllaDB

DynamoDB は「論文で提案された DHT アルゴリズムを Amazon がマネージドサービス化した」と言える。

4. Consistent Hashing の要点

素朴な hash(key) % N だとサーバー追加でほぼ全データが再配置される。

Consistent Hashing のアイデア:

ハッシュ値空間を「円環」として扱う（0 〜 2^32 の円）:

          0
      ┌───┴───┐
   サーバーA          サーバーB
      │                │
      └───┐       ┌────┘
          サーバーC

key をハッシュして円上に配置 → 時計回りに最初にぶつかったサーバーがその key の担当

サーバーを追加しても隣接区間のデータだけが再配置される。O(N) ではなく O(K/N) の移動で済む。これが DynamoDB が裏で動的にパーティションを増減できる仕組み。

5. Redis / Memcached との違い

同じ「キーバリュー型 NoSQL」でもアーキテクチャが異なる:

RedisMemcachedDynamoDB
データ構造多様（リスト、ハッシュ、セット、etc）単純なKVKV + SK ソート + JSON
永続化あり（RDB/AOF）なし（メモリのみ）あり（マネージド）
分散Redis Cluster で後付けクライアント側でシャーディング最初から分散前提
用途キャッシュ + データ構造純粋キャッシュプライマリDB

DynamoDB は「最初から分散前提で設計された、永続化されるハッシュテーブル」という立ち位置。

6. PK の部分一致検索は原理的に不可能

ハッシュ関数の性質から、PK の部分一致（begins_with, LIKE, 範囲）は原理的にできない。

hash("user-001")   = 0x8a3f2c91...   → パーティション A
hash("user-002")   = 0xd7e14f23...   → パーティション C
hash("user-003")   = 0x1b9c8a77...   → パーティション B
hash("user-0001")  = 0x4d2e91bc...   → パーティション A
hash("user-0002")  = 0xf08a7c15...   → パーティション B

ハッシュ関数は「似た入力を似た出力に変換しない」のが重要な性質（1文字違うと全く違う値になるよう設計されている）。

つまり「user-1 で始まるキー」を探そうとすると:

  • その接頭辞を持つキーは全パーティションに散らばっている
  • 結果として「全サーバーに聞いて回る」しかない
  • 分散システムの旨みが全くない、単なる全走査になる

「できない仕様」ではなく、「できたら DHT の意味が崩壊する」という話。

PKで部分一致したいときの対処

対処概要向いている場面
データモデル見直し前方一致したい部分を SK に切り出す設計段階（推奨）
GSI で別キーを張る完全一致できる粒度まで分解した属性で GSI を作る後からの要件追加
Scan + Filter全件読んでフィルタ絶対にやるな（コスト爆発）
OpenSearch 連携DynamoDB Streams → OpenSearch へ流す全文検索・曖昧検索

7. SK はソート可能なスカラー型のみ

SK に使える型は以下の3つ:

型説明ソート順
String (S)文字列UTF-8 バイト列の辞書順
Number (N)数値数値順
Binary (B)バイナリバイト列順

SK に使えない型: List, Map, Set, Boolean, Null。

なぜか: パーティション内部は B-tree / skip list で管理されていて、B-tree は「任意の2要素で比較可能」「全順序」を要求する。List や Map には全順序が定義できない。

複合情報は文字列エンコードで詰め込む

「スカラー型のみ」と言っても、文字列にエンコードすれば多次元情報を持てる:

SK: "2024-01-15#AC#abc300_a"
     日付       結果 問題ID

辞書順ソートなので、以下の順に並ぶ:
  "2024-01-15#AC#abc300_a"
  "2024-01-15#WA#abc300_a"
  "2024-01-16#AC#abc300_b"

ポイント: DynamoDB は「複合SK」という型を持たない。文字列の辞書順比較を利用して、アプリ側が多次元情報を1次元にエンコードしている。

ISO日付フォーマット（YYYY-MM-DD）やゼロパディング数値（00001）が多用されるのは、辞書順 = 意味的な順序になるように工夫しているため:

❌ "1", "10", "2" → 辞書順だと "1", "10", "2"（10 が 2 より前）
✅ "001", "002", "010" → 辞書順で "001", "002", "010"（正しい順）

8. PK と SK の非対称性

PK と SK は対等な「2つの主キー」ではない。物理シャーディングの都合で役割が違う。

できること:
  Query(PK="user-123") → このユーザーの全SKを取得 ✅
  GetItem(PK="user-123", SK="SUB#00042") → 1件ピンポイント ✅

できないこと:
  Query(SK="SUB#00042") → この submission を持つ全ユーザーを取得 ❌
  Query(SK begins_with "2024-01") → 2024年1月の全データを全ユーザー横断 ❌

分散の物理構造:

パーティション A: (user-123, SUB#00042)  ← ここに物理的に存在
パーティション B: (user-456, SUB#00042)  ← ここにも存在（同じSK値）
パーティション C: (user-789, SUB#00042)  ← ここにも

「SK = SUB#00042 を全て取得」するには全パーティションを走査するしかない。それは Scan。

対称性のまとめ

観点PKSK
役割物理パーティション決定パーティション内ソート
データ構造ハッシュテーブルB-tree
計算量O(1) 配置O(log n) 探索
横断クエリ❌（全サーバー走査）❌（PK指定なしでは不可）
ピン止め後❌ 完全一致のみ✅ 範囲クエリOK

9. 多対多リレーションは Inverted GSI で

「SK 側から逆引きしたい」= 多対多検索は、PK と SK を入れ替えた GSIで解決する定石パターン（Inverted Index）。

元テーブル submissions:
  PK = user_id, SK = problem_id
  → Query(PK="user-123") で「user-123 が解いた全問題」 ✅
  → しかし「abc300_a を解いた全ユーザー」は ❌

GSI "InvertedIndex":
  GSI PK = problem_id  ← 元のSKをPKに
  GSI SK = user_id     ← 元のPKをSKに
  → Query(GSI, PK="abc300_a") で「この問題を解いた全ユーザー」 ✅

物理的には別のハッシュ関数で再分散されている:

元テーブル: hash(user_id) で分散
  サーバーA: user-123 の全submissions
  サーバーB: user-456 の全submissions

GSI: hash(problem_id) で再分散（コピー）
  サーバーX: abc300_a の全submissions
  サーバーY: abc300_b の全submissions

「双方向検索したい」＝「両方向でハッシュし直した物理配置が必要」＝ ストレージとスループットコストが倍。

10. この視点から見える設計原則

洞察設計原則
PK はハッシュで物理配置PK 設計 = 物理配置設計
SK はソート可能な型のみ複合情報は文字列にエンコード
PK/SK は対等でない双方向検索は GSI で倍のコストを払う
分散してるから横断クエリ不可クエリしたい軸の数 = 必要な GSI の数

DynamoDB の設計 = 「ハッシュテーブルを何枚張るか」の設計と言い換えられる。

RDB が「1つのテーブルにインデックスを後付けで足す」のに対し、DynamoDB は「アクセスパターンごとに別の物理配置（ハッシュテーブル）を用意する」アーキテクチャ。

Q&A

Q: DynamoDB はどちらかというとハッシュテーブルだよね?

その通り。「分散ハッシュテーブル（DHT）」そのもの。競プロ的に言えば unordered_map<PK, map<SK, Item>> が複数サーバーに分散している構造。Amazon の Dynamo 論文（SOSP 2007）が起源で、Cassandra / Riak / ScyllaDB もこの系譜の子孫。

Q: PK の部分一致検索（begins_with, LIKE など）はできない?

原理的に不可能。ハッシュ関数は「似た入力を似た出力に変換しない」性質を持つため、接頭辞が同じキーも全パーティションに散らばっている。できるようにすると全サーバー走査になり DHT の意味が消える。

対処は「データモデル見直し（前方一致したい部分をSKに切り出す）」「GSIで別キーを張る」「全文検索が必要なら OpenSearch に流す」のいずれか。Scan + Filter は最終手段（コスト爆発するので非推奨）。

Q: SK はソート可能なデータしか配置不可能?

正しい。SK に使えるのは String / Number / Binary の3つのスカラー型のみ。パーティション内部が B-tree で管理されていて、B-tree は「任意の2要素で比較可能」「全順序」を要求するため、List や Map のような全順序が定義できない型は入らない。

ただし複合情報を扱いたい場合は 文字列にエンコードする（例: "2024-01-15#AC#abc300_a"）ことで多次元情報を1次元の辞書順に変換できる。これが DynamoDB の複合SKパターンの正体。

Q: PK と SK が多対多の対応不可能なのは分散しているから?

その通り。PK と SK は対等な2つの主キーではなく、PK = 物理パーティション決定 / SK = パーティション内ソート という非対称な役割を持つ。「SK だけで横断検索」ができないのは、SK が同じアイテムが全パーティションに散らばっているため（全サーバー走査になる）。

多対多が必要なら PK と SK を入れ替えた GSI（Inverted Index） を張る。物理的に別のハッシュ関数でデータをコピーし直すため、ストレージとスループットが倍になるのが代償。

ハンズオン — 実 AWS sandbox を動かす

普段は無料で検証し、CloudWatch を見たい時だけ短時間 apply→観測→destroy します。apply から実課金。終わったら必ず destroy。

  1. 無料検証（課金なし）make sandbox-test-phase1
  2. デプロイ（実課金開始）make sandbox-up-phase1
  3. 負荷生成 — 無認証トラフィックを生成（認証あり負荷は TEST_PASSWORD=... を付ける）make sandbox-load-phase1
  4. 観測 — API GW の Count/4XXError/Latency、Lambda、DynamoDB、Cognito メトリクスmake sandbox-watch-phase1
    ⏱ 反映まで 2〜5 分
  5. 後片付け（課金停止）make sandbox-down-phase1

⚠ phase1 は本番スタックを観測するダッシュボードのみ作成（本番アプリは別途デプロイ済みが前提）。
