なぜ CORS が必要なのか — 「サーバが許可してサーバが防ぐ」ではない3者構造

種別: ユーザー議論・Q&A の記録（Phase 1 / Task 3）
関連教材: 01-lambda-response-format-and-cors.md
関連reference: cors-only-blocks-reads-not-writes.md, samesite-cookie-and-csrf-defense.md

論点

ユーザーが CORS の本質に対する違和感を表明:

CORS ヘッダが必要な理由がわからないというか、自分で許可して自分で防ぐということなの

サーバ自身がレスポンスヘッダで「許可するオリジン」を書き、それでサーバ自身が守られているように見えるが、本当にそうなら「サーバが自分のルールでサーバ自身を守ってる」だけで、攻撃者は別経路で攻めればいいのではないか、という構造的な疑問。

実はこの違和感は正しく、CORS の登場人物は3者で、誰が誰を守っているのかを正しく分解しないと「自己完結したお遊び」に見えてしまう。

Q&A

Q1: CORS は「サーバが自分で許可して自分で防ぐ」だけのものなのか？

違う。3者の協調で成立する仕組み。

役何をしているか
サーバ「誰が読んでいいか」を宣言する（レスポンスヘッダで）
ブラウザサーバの宣言を読んで、ユーザーのために執行する
ユーザー守られる対象（自分のログイン中のセッションが悪用されないように）
 
サーバ:   「読んでいいのは app.example.com からだけ」と宣言
ブラウザ: 「じゃあ evil.com の JS にはレスポンスを渡さない」と実行
ユーザー: 知らないうちに守られている

「サーバが許可してサーバが防ぐ」ではなく 「サーバが宣言、ブラウザが執行、守られるのはユーザー」。守る側と守られる側が分離している。

Q2: なぜサーバは自分で防げないのか？

サーバは「JS の出どころ」を確実には判定できないから。

サーバから見えるリクエスト:

GET /submissions HTTP/1.1
Host: api.example.com
Origin: https://evil.com    ← 自己申告。curl で偽装可能
Authorization: Bearer eyJxxx...
Cookie: sessionId=abc123

Origin ヘッダはブラウザが付けるが、curl や Postman なら任意の値を付けられる:

curl -H "Origin: https://app.example.com" https://api.example.com/...

つまりサーバが Origin ヘッダを見て弾いても意味がない（攻撃側は直接 curl を使えばいい）。

そもそもサーバ単独でクロスオリジン攻撃を防ぐのは不可能で、「JS の出どころを唯一確実に知っているのはブラウザ」。だから防御をブラウザに任せる構造になっている。

Q3: ブラウザはなぜ JS の出どころを確実に知れるのか？

JS を実行しているのがブラウザ自身だから。

window.location = https://evil.com    ← ブラウザは自分で知っている
   ↓
JS が fetch("https://api.example.com")
   ↓
ブラウザ: 「fetch を呼んだのは evil.com の JS だ」 ← 確定情報
   ↓
レスポンスが到着、サーバは Allow-Origin: https://app.example.com と返した
   ↓
ブラウザ: 「evil.com 経由だから JS には渡さない」

ブラウザ内部の状態として「今 JS を実行しているページのオリジン」が保持されている。これは外部から偽装しようがない。

サーバから見るとリクエストは「ブラウザが付けた Origin ヘッダ」しか手がかりがない（その Origin も非ブラウザクライアントなら任意）。一方、ブラウザは内部状態として確実に知っている。

Q4: もし CORS が完全に無い世界だとどうなる？

3パターンを並べると CORS の存在意義が見える:

状態動作結果
CORS 無し / SOP 厳格クロスオリジン fetch を全部禁止正当な CDN・地図API・OAuth・決済が全部死ぬ → Web 崩壊
CORS あり (今)サーバが許可リストを宣言、ブラウザが執行正当な通信 OK、攻撃遮断
CORS で * 全許可サーバが「誰でも OK」と宣言防御ゼロ、ログイン中ユーザーがデータ漏洩

CORS あり は「サーバが能動的に正しい設定をする」ことが前提のシステム。* にしたら意味がないし、何も書かなければデフォルト deny で正当な通信もできない。サーバが意識的に許可宣言するのがポイント。

Q5: 結局 * にしたら意味ないなら、CORS は無意味では？

仕様レベルで * を制限する仕組みが入っている:

  1. Allow-Origin: * + Allow-Credentials: true は仕様で禁止
    • Cookie や Authorization をクロスオリジンで送るときは、必ず具体的なオリジンを指定する必要がある
    • 認証情報を伴う場合の * をブラウザが拒否する
  2. 本番では具体的なオリジンを指定するのが原則
    • 開発の * は「あらゆる localhost ポート」「自動デプロイ環境のドメイン」のような開発時の利便性のため
    • 本番デプロイ時は許可オリジンの限定が運用ルール
  3. CSP (frame-ancestors など) との組み合わせで多層防御

つまり CORS 単体で見ると「サーバの設定次第で骨抜きになる」のは事実だが、仕様で * の濫用を防ぎ、運用ルールで限定を強制することで実効的な防御になる設計。

Q6: メタな構図で整理すると？

ブラウザはユーザーの代理人。

[ユーザー]
   ↓ 「私の代わりに Web を見て、危ない情報は JS に渡さないで」
[ブラウザ]
   ↓ サーバの Allow-Origin を読む
[サーバ]
   ↓ 「私のフロントだけが読んでいい」
  • サーバは自分の都合を表明する（誰に見せていいか）
  • ブラウザはユーザーの都合を実装する（変なサイトに自分のデータを盗まれたくない）
  • 両者が協力して初めて成立するシステム

「サーバが許可して、サーバが防ぐ」のではなく「サーバが宣言し、ブラウザがユーザーのために執行する」と理解すると違和感が消える。

サーバの宣言は「外向きの policy」、ブラウザの執行は「ユーザーの代理人としての判断」、という非対称な役割分担。

結論 / 整理

CORS は 3者協調システム:

  1. サーバ = 政策決定者（誰に見せるか）
  2. ブラウザ = 執行者（policy を読んでユーザーを守る）
  3. ユーザー = 受益者（守られる対象）

「自分で許可して自分で防ぐ」と見えるのは、サーバ＝防御主体と勘違いしているから。実際は 守られているのはユーザー、執行者はブラウザ、サーバはルールを公開してるだけ。

サーバは JS の出どころを判定できない（Origin ヘッダ偽装可能）→ ブラウザに執行を委ねざるを得ない、という非対称性が CORS の根本的な構造。

比較表 / 具体例

各登場人物の責務

登場人物責務できないこと
サーバ「許可するオリジン・メソッド・ヘッダ」を宣言JS の出どころを判定する（Origin 偽装可能なので）
ブラウザサーバの宣言を読み、JS にレスポンスを渡すか判定サーバの policy を勝手に決める
ユーザー認証セッションを持つCORS の判定に介入する（自動的に守られる）

防御の主体は誰か（攻撃別）

攻撃防御主体防御手段
クロスオリジン読み取りブラウザ（サーバの宣言に基づく）CORS / SOP
クロスオリジン書き込み (CSRF)ブラウザ + サーバSameSite Cookie / CSRF トークン / JWT in Header
同一サイト内 XSSサーバ + ブラウザCSP / 入力サニタイズ
サーバへの直接 API 攻撃 (curl)サーバのみ認証 / Rate Limit / WAF

CORS が効くのは「ブラウザを介した攻撃」のみ。curl で直接叩く攻撃には CORS は無力で、別の防御（認証、WAF）が必要。

「自己完結に見える」を払拭する考え方

誤った見方:
  サーバ → CORS ヘッダ → サーバを守る （自己完結）

正しい見方:
  サーバ → CORS ヘッダ → ブラウザに policy 通知
                         ↓
                       ブラウザ → ユーザーのセッションを守る

policy の宣言と執行が別主体に分離されている、という非対称性が CORS の本質。

よくある誤解

  • 誤解: CORS はサーバが自分で防御する仕組み
    • 実際: サーバが policy を宣言し、ブラウザが執行する。守られるのはユーザー
  • 誤解: サーバが Origin ヘッダを見て弾けば CORS と同じ防御になる
    • 実際: Origin は curl で偽装可能。ブラウザでないと信頼できる判定はできない
  • 誤解: CORS でサーバ自体のセキュリティが上がる
    • 実際: サーバは curl で叩けば直接アクセスできる。CORS が守るのはブラウザ越しのユーザー
  • 誤解: * で全許可にしておけば便利かつ安全
    • 実際: Allow-Credentials: true と * は併用禁止。認証付きでは具体オリジン指定が必須
